# 第十三章 智能体安全架构

防御只有四种形态：隔离不可信内容、收窄敏感访问、管住对外动作，三项都必须保留时则加监督。本章讨论动作闸和这四种形态在架构上的实现，范围限于模型出错或被说服之后仍然成立的机制：能力拆分、控制流与数据流隔离、沙箱与出站控制、身份与委托（不问原因的不可逆操作网关见 [13.1.5](13.1_agents_rule_of_two.md)）。使模型“更难被骗”的措施有用，但只能降低频率，不能设定上界，这类措施在[第四章](../04_prompt_injection/README.md)和[第九章](../09_io_protection/README.md)讨论。[第十四章](../14_agent_practice/README.md)把本章的方法应用于一个完整系统，并给出全景图与评审清单。

## 学习目标

读完本章，读者应能：

1. 用 Rule of Two 判断一个智能体在单个会话内是否同时具备不可信内容、敏感访问、对外动作三项，并说明应去掉哪一项、由什么机制保证。
2. 用“攻击者完全控制模型输出后是否仍然成立”这一标准区分架构级防御与概率性防御，并说明双 LLM、CaMeL、信息流控制、策略化权限控制各自保证的性质与代价。
3. 检查一个沙箱是否同时隔离了文件系统与网络、凭据是否留在沙箱之外，并找出未纳入沙箱的执行路径。
4. 区分共享服务账号、冒充用户与显式委托三种做法，说明委托链中的权限如何衰减、由谁执行。
5. 为每一类安全工具判断它提供确定性保证还是只降低频率，并核对其文档写明的边界。
6. 在 OpenAI Agents SDK、Claude Agent SDK、LangGraph 或 Google ADK 中，把同一个确定性策略挂到工具调用之前，并让人工确认绑定具体参数。

## 本章结构

- [13.1](13.1_agents_rule_of_two.md) Rule of Two 与能力拆分：一个会话内三项条件如何去掉其一、三项都需要时如何监督，以及已披露案例的检验
- [13.2](13.2_architectural_defenses.md) 提示注入的架构级防御：假设模型一定会被骗，如何用六种设计模式、CaMeL 与信息流控制，使不可信数据无法改变控制流、敏感数据无法流向未授权出口
- [13.3](13.3_sandbox_egress.md) 执行沙箱与出站控制：文件系统、网络与凭据三条边界如何在操作系统和网络层实现
- [13.4](13.4_agent_identity.md) 智能体身份与委托授权：智能体以什么身份访问资源，权限如何随委托衰减
- [13.5](13.5_tooling_selection.md) 工具与方案选型：策略引擎、护栏、网关、MCP 扫描、沙箱、身份、可观测性与红队八类工具，各自保证什么、文档承认不做什么
- [13.6](13.6_framework_gates.md) 在主流智能体框架中实现闸：同一个确定性策略在四个主流框架中挂在哪里、怎样拒绝或要求确认、确认怎样绑定参数，以及各框架挂载点的覆盖缺口

前两节讲设计原则：13.1 从能力组合上限制最坏情况，13.2 讲假设模型一定会被骗时，如何用架构保证控制流与数据流的性质。13.3 与 13.4 讲支撑这些原则的两类基础设施，即执行环境与身份。13.5 把前四节的机制对应到可用的工具上，13.6 再把闸落到开发者实际使用的智能体框架中。
