# 实验二：可信预算状态

100 元预算不能由每次请求独立核验：两个并发的 60 元请求都可能在检查时看到 100 元可用。本实验把授权范围、操作绑定和预算状态放入同一个本地 SQLite 数据库，以事务完成检查与预留，演示第 11.7 节的跨请求边界。全部用户、商户、金额和查询结果均为合成数据，不连接支付网络。

源码：[`examples/payment_budget/ledger.py`](ledger.py)；测试：[`tests/test_payment_budget.py`](../../tests/test_payment_budget.py)。

## 运行与预期结果

从本书根目录运行，仅使用 Python 标准库：

```bash
python3 examples/payment_budget/ledger.py
python3 -m unittest discover -s tests -p test_payment_budget.py -v
```

第一条命令创建临时数据库，输出 JSON 后自动清理。`simulation` 和 `passed` 应为 `true`，五个案例的 `passed` 均应为 `true`；任一效果验收失败，命令退出码为非零。第二条命令包含真实数据库的功能测试和三个受控变异测试。

| 案例 | 应观察到的结果 | 可用金额（分） |
| --- | --- | --- |
| 正常预留并确认执行 | `RESERVED → SETTLED` | 4000 |
| 两个连接并发请求 60 元 | 一个 `RESERVED`，另一个 `BUDGET_EXCEEDED` | 4000 |
| 同编号同参数重放，再改金额 | 重放返回原状态，改金额被 `OPERATION_CONFLICT` 拒绝 | 7000 |
| 超时后仍无法确认，再确认执行 | 保持 `UNKNOWN`，同编号返回 `UNKNOWN`；新编号的 60 元请求超预算；确认执行后 `SETTLED` | 4000 |
| 查询确认未执行 | `UNKNOWN → CANCELLED` | 10000 |

并发案例不规定哪个线程先成功。金额固定为人民币分：100 元写作 `10000`，60 元写作 `6000`。金额与预算必须为正整数，拒绝零、负数、布尔值、浮点数、字符串和超出 SQLite 有符号整数范围的值。

## 两张表与事务边界

`grants` 是可信侧预先写入的授权记录，保存预算、用户、接收方和失效时刻。演示固定用户 `alice`、接收方 `shop`、预算 `10000` 和失效时刻 `1000`，请求使用合成时刻 `100`。已有授权不能被覆盖以重置预算。真实系统应由可信身份与授权流程提供这些记录，不能让模型调用初始化接口生成授权。

`operations` 保存全局唯一操作编号、关联授权、规范化参数、金额和状态。规范化参数包含授权编号、用户、接收方、金额与固定币种 `CNY`，以 JSON 数组稳定序列化，使用参数化 SQL 写入。相同编号的任一业务参数不同即拒绝；全部相同则返回已有状态，不再次扣减。检查重放先于期限检查，因此到期后仍可查询原操作状态，但不能产生新预留。合成时钟不是业务参数；真实系统应使用可信时钟。

每个调用方使用独立连接。[SQLite 事务文档](https://www.sqlite.org/lang_transaction.html#deferred_immediate_and_exclusive_transactions) 说明 `BEGIN IMMEDIATE` 立即开始写事务，数据库同时只允许一个写事务。`reserve` 在该事务内读取操作、核验授权范围与期限、计算可用金额并插入预留。成功才提交；失败回滚。预算计算为：

```text
可用预算 = 授权预算 − SUM（RESERVED、UNKNOWN、SETTLED 的金额）
```

`SETTLED` 是已消耗预算；`RESERVED` 和 `UNKNOWN` 是仍被占用的预算。`CANCELLED` 不占额度。状态更新与余额快照也在事务内完成。本实验只覆盖共享同一个数据库的调用方，不对独立数据库、多地区服务或支付网络提供统一额度保证。

## 超时与终态

| 当前状态 | 可信观察 | 下一状态 | 预算处理 |
| --- | --- | --- | --- |
| `RESERVED` | 请求超时 | `UNKNOWN` | 保留 |
| `RESERVED` 或 `UNKNOWN` | 查询确认已执行 | `SETTLED` | 保留为已消耗金额 |
| `RESERVED` 或 `UNKNOWN` | 查询确认未执行 | `CANCELLED` | 释放 |
| `UNKNOWN` | 仍无法确认 | `UNKNOWN` | 保留 |
| `SETTLED` 或 `CANCELLED` | 同一结果重复确认 | 原状态 | 不变 |
| `SETTLED` 或 `CANCELLED` | 相反结果或改为未知 | 拒绝转换 | 不变 |

`reconcile(executed=True/False/None)` 的输入代表可信查询结论，不能来自模型判断、商户页面文字或一次网络超时。`False` 必须表示确定未执行，而不是“没有收到成功响应”。无法确认时继续保留额度，等待查询或人工处理。

返回已有 `RESERVED`、`UNKNOWN` 或终态仅表示账本状态，不构成再次执行支付的许可。调用方不能通过改用新编号重试同一笔未知支付；演示中的新编号请求用于验证占用额度，真实支付重试还需要执行端的幂等绑定。本实验没有支付执行器、事务发件箱或远程重试机制。

## 验收如何证明会失败

测试先建立语义验收：尚未实现的预留返回 `UNIMPLEMENTED`，与预期 `RESERVED` 不符，测试失败。实现后验证并发连接、重放、变参、用户与接收方范围、到期、金额类型、状态持久化和终态边界。

变异测试加载本地源码的受控副本，在真实临时数据库上运行相同验收，不替换函数返回值：

- 去掉事务锁与整笔提交，以同步屏障强制两个连接先读取余额再插入。两个 60 元预留均成功，相同并发验收必须拒绝。
- 去掉操作编号主键及重放绑定分支。同编号发生真实重复插入，预算被再次占用，相同重放验收必须拒绝。

变异只存在于测试进程的内存中，不改动交付源码。完整测试命令显示变异测试通过，表示验收确实抓住了错误版本。

## 与 AP2 的关系及边界

[AP2 Payment Mandate](https://ap2-protocol.org/ap2/payment_mandate/#budget) 定义预算约束时明确要求跟踪累计金额，批准后累加；签名约束本身不能替代可维护的跨请求状态。[Double Spend](https://ap2-protocol.org/ap2/security_and_privacy_considerations/#double-spend) 要求避免在未收到拒绝回执时签发重叠授权，并保护回执完整性。[Agent Authorization](https://ap2-protocol.org/ap2/agent_authorization/#action-authorization) 定义验证授权和签名回执的流程。上述协议要求不应被解读为自动提供全球统一账本；本实验选择本地事务来演示预算状态，不声称实现 AP2。

本实验不实现签名验证、授权链、支付回执验签、IAM、网络访问控制、支付凭据管理、撤销、退款或币种换算，也不提供防止数据库被篡改的权限边界。运行代码的进程可写数据库，因此部署时必须把账本放在模型无法直接修改的可信服务内，按真实支付端的确认语义设计对账与执行幂等。实验只验证这里列出的本地状态契约。
