## 7.3 检索结果操纵

检索结果操纵是指攻击者试图操纵检索过程，使恶意内容优先被返回。与上一节的“入库投毒”相比，本节关注污染内容如何进入 top-k 结果，回答三个问题：攻击者用哪些手段影响排序，检索器层面能做什么，以及如何判断“文档被召回”究竟发生在哪一环节。结论是：混合检索、重排等检索侧措施只提高攻击成本，检索侧的硬约束是按可信身份限制可交付的文档，而**授权只保护机密性，不能保证允许读取的内容未被投毒**。下面依次介绍操纵手法、检索器层面的对抗和从候选到答案的诊断链。

### 7.3.1 操纵手法

常见的操纵手法有三种：嵌入相似度攻击、关键词堆叠和元数据利用。

嵌入相似度攻击针对稠密检索：攻击者分析目标查询的嵌入向量，构造嵌入向量与之接近的文档并上传，使目标查询发生时恶意文档被检索（图 7-3）。

```mermaid
flowchart LR
    A["分析目标查询<br/>的嵌入向量"] --> B["构造文档使其<br/>嵌入向量接近"]
    B --> C["上传恶意文档"]
    C --> D["目标查询时<br/>恶意文档被检索"]
```

图 7-3：检索结果操纵流程图

关键词堆叠是指在恶意文档中包含相关关键词，尝试影响稀疏检索或混合检索信号。能否提高稠密检索排名需用实际嵌入与排序验证，词频增加本身不构成证据。

元数据利用是指利用文档元数据（如标题、标签）影响检索排序。

### 7.3.2 检索器层面的对抗

检索器层面的防御只能提高攻击成本，不能设定上界。若把投毒视为针对检索器的搜索引擎优化（[7.2](7.2_knowledge_base_poisoning.md) 节的 GASLITE），防御也可以从检索器入手：混合检索（稀疏加稠密）提高了同时欺骗两种信号的难度，重排器与多来源一致性检查提高了单条恶意文本主导结果的难度。但攻击者可以联合优化两种信号（[附录 C-284](../16_appendix/C_references.md)），重排器本身也是模型。

检索侧的硬约束是用可信身份强制限制可交付的文档（[7.6](7.6_retrieval_access_control.md) 节）；来源信誉、相似度和重排分数只是相关性或风险信号，不能授予读取权限，也不能保证允许读取的内容未被投毒。

### 7.3.3 从候选到答案的可诊断链

说“文档被召回”时，至少要说明它到达了哪一环节：原始候选、授权候选、重排后的 top-k，还是实际被上下文预算保留的片段。每一环节保留受保护的文档 ID、分数、排名与裁剪原因，才能分辨是检索未命中、ACL 拒绝、重排靠后、上下文截断，还是生成阶段没有服从载荷。诊断轨迹同样受访问权限约束，生产日志不应为排障复制未授权正文。

```mermaid
flowchart LR
    A["候选 ID / score / rank"] --> B["可信身份 + ACL<br/>允许的候选 ID"]
    B --> C["重排 / top-k / 预算"]
    C --> D["复核授权<br/>构建实际 context"]
    D --> E["生成输出"]
    E --> F["独立 oracle<br/>目标答案 + 正常效用"]
```

图 7-4：应用可观察的检索与授权链。授权在正文交付前执行；图中候选轨迹不表示所有向量索引必须采用同一种内部遍历顺序。

下面的例子说明授权与内容可信是两回事。固定分数为 `private=0.99、poison=0.95、clean=0.80、clean2=0.70`，当前用户只能读后三份文档，`k=2`。授权后的上下文是 `poison、clean`：排名第一的未授权文档被拒绝，但允许读取的投毒文档仍进入了上下文。ACL 保护的是机密性，不能据此认定内容可信或生成安全。

[可运行的合成实验](../examples/rag_trace/README.md)分别固定上下文测试生成、固定载荷测试候选变化，并输出每一环节的证据；固定分数用于隔离控制逻辑，不是向量排名攻击实验。
