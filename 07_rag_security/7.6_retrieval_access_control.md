## 7.6 检索时的访问控制

企业 RAG 最常见的泄露不是被攻击者投毒，而是把用户本来无权看到的文档检索了出来。知识库通常汇聚了许多系统的数据，而这些系统各有自己的权限模型；检索一旦绕开这些权限，模型就成了一个替所有人读所有文档的代理。本节讨论权限应当在检索的哪一步执行、用什么机制执行，以及主要云平台提供了什么。

### 7.6.1 授权必须先于内容交付

向量检索的访问控制通常以元数据过滤实现：每个切块带有允许访问的用户或组标识，查询时附带当前用户的身份做过滤。必须守住的不变量是：**未经当前用户授权的正文，不得进入模型上下文，也不得交给无权读取它的重排服务、缓存或日志**。服务内部为搜索维护或遍历向量节点，与向应用返回正文是两个不同的边界。

- **服务内前过滤**：在搜索中应用过滤谓词，再形成符合条件的 top-k。Azure AI Search 的 `preFilter` 在各分片的 HNSW 遍历期间应用过滤，并非要求所有 ANN 都在遍历任何节点前先生成完整允许列表。
- **服务内后过滤**：Azure 的 `postFilter` 先形成各分片的未过滤候选，再在服务内部裁剪、合并；`strictPostFilter` 则在全局 top-k 之后裁剪。若授权条件可信且结果在交付前已正确过滤，不能仅凭“后过滤”就断定泄露。候选被提前截断却会漏掉排名较低的授权文档；前过滤更有利于授权召回，选择性很强时也可能增加遍历成本（见 Azure 的[向量过滤文档](https://learn.microsoft.com/en-us/azure/search/vector-search-filters)，以及附录 C-198、C-199）。
- **应用收到正文后才过滤**：若未授权正文先进入无权组件、共享缓存或日志，最后从回答里删除也无法收回暴露。应把授权推到内容交付边界；即使应用是获准读取全部文档的受信组件，也应最小化读取并在构建终端用户上下文前强制检查。

**授权过滤条件必须由应用根据已认证的终端用户、租户和资源范围生成，不能由不可信输入拼接，也不能由模型决定。** 2026 年披露的 Spring AI 向量存储过滤表达式注入漏洞（CVE-2026-41705，附录 C-191）说明了后果——过滤表达式若由未经处理的文档标识拼接而成，过滤本身就可以被改写。Azure 的安全过滤器本身只是字符串比较，并不认证传入的主体，必须对每次查询强制应用可信过滤条件（附录 C-203）。模型生成的相关性过滤可以与它取交集，不能替代或放宽它。分块、重排、缓存命中后也要保持该约束；源权限撤销到索引同步之间的窗口须有明确策略（附录 C-202）。

### 7.6.2 云平台的参考设计

三家主要云平台都提供了文档级的检索时访问控制，设计思路相近，但各有需要注意的细节（附录 C-200 至 C-205）：

| 平台 | 机制 | 要点与边界 |
|------|------|------------|
| Amazon Bedrock Knowledge Bases | 元数据过滤：文档旁放置 `.metadata.json` 声明属性，查询时在检索配置中传入过滤器 | 过滤值由调用方提供，平台不做身份到权限的映射；应用必须自己保证过滤器不可被用户输入篡改。另有由模型生成的隐式元数据过滤，不应用于访问控制 |
| Azure AI Search | 文档级访问控制：安全过滤器（应用把用户或组标识作为字符串传入过滤）；类 POSIX 的 ACL 与 RBAC 范围（预览）；Purview 敏感度标签与 SharePoint ACL（预览） | 安全过滤器模式“通过安全主体本身不做任何认证或授权”，只是字符串比较；原生 ACL 方式在请求头中附带用户令牌，由服务比较令牌声明与文档权限元数据。文档明确两个陷阱：源系统的权限变更要等元数据同步后才生效；分块索引必须把权限元数据投影到每个切块（文档以敏感度标签为例指出，不投影则切块级引用不会被过滤） |
| Google Agent Search（原 Vertex AI Search） | 数据源访问控制：按文档声明读者主体，由身份提供方识别终端用户并判断其是否有权看到结果 | 支持 Cloud Storage、BigQuery、Google Drive 与第三方数据源；每份文档最多 3,000 个读者主体 |

AWS 另有 Kendra 的用户上下文过滤——由连接器在抓取时收集源系统的访问控制列表，查询时按用户上下文裁剪——但其 GenAI 企业版索引不支持基于令牌的方式，且该服务已不再接受新客户，不宜作为当前推荐路径（附录 C-282）。

### 7.6.3 过度共享：权限本身就是错的

权限过滤正确执行，不等于结果正确。企业系统里大量内容的权限设置过宽而无人知晓，RAG 把这类内容带到了所有人面前。微软关于 Microsoft 365 Copilot 的文档直接描述了这一情形：某个站点可能对一些本不该看到它的用户开放，当这样的用户向 Copilot 询问预算信息时，Copilot 会从该站点取得内容（附录 C-205）。微软为此提供的“受限 SharePoint 搜索”被其文档明确标注为“不是安全边界，也不改变站点权限”，只是过渡措施，并将停止新启用；推荐路径是识别并修复过度共享，再配合敏感度标签与数据防泄漏。

这给出了企业 RAG 上线前的一条检查项：**先修权限，再接知识库**。把知识库接入前，用权限审计工具找出“所有人可读”的内容和继承链异常的站点；上线后把“检索到了不该检索的内容”作为一类独立的事件来监控。

### 7.6.4 混淆代理：RAG 替攻击者读文档

即使权限正确、授权先于上下文构建，RAG 仍可能被攻击者当作代理。研究者在 Copilot for Microsoft 365 上展示了一类被称为 ConfusedPilot 的问题：攻击者只需在自己有权写入的位置放入内容，就能让 RAG 在回答其他用户的问题时产生完整性与机密性违规，其中一种手法利用检索过程中的缓存机制泄露秘密数据（附录 C-214）。另一个演示针对 Slack AI：攻击者独自创建一个公开频道并写入指令，Slack AI 在回答其他用户关于密钥的问题时检索到这条指令，把密钥嵌进一个钓鱼链接渲染出来（附录 C-213）。两者都不需要越权读取——攻击者写入的是自己有权写入的地方，越权的是读取时的推理。

这类问题的根源是检索结果被当作指令处理，解决方法在第十二章与第十三章：检索到的内容按不可信输入处理，由没有工具的模型实例读取，只有其中的获准标量进入决策（13.2.2）。

> **本节要点**
> - 授权必须在正文交付与上下文构建前强制执行；ANN 内部前后过滤另有召回与成本权衡。过滤条件由应用按已认证身份生成，模型不能放宽它。
> - 云平台都提供文档级过滤，但各有边界：权限同步有滞后，切块必须继承权限，安全过滤器本身不做认证。
> - 过滤正确不等于权限正确：先修过度共享，再接知识库；攻击者在自己有权写入的位置放内容，就能让 RAG 替他读文档。
