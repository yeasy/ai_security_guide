### 3.1.1 OWASP 与 LLM Top 10 背景

OWASP 是非营利安全社区组织，长期维护 Web 安全、API 安全与 AI 安全相关实践。
LLM Top 10 的价值在于：把“模型风险”转译成“应用系统风险”，便于工程团队落地治理。

**十大风险常常共现，但不应被理解为固定攻击链**

阅读下面的十个风险项时，重要的是理解它们之间可能相互放大，而不是把它们视为严格独立、也不是把它们理解为固定顺序的攻击链。在真实系统中，多个风险常常同时出现：
- **提示注入（LLM01）** 可能与隐藏上下文暴露（LLM08）、过度自主权（LLM03）或敏感信息泄露（LLM02）同时出现
- **供应链风险（LLM04）** 与 **数据与模型投毒（LLM05）** 都属于“源头污染”问题，但影响面和发生位置并不相同
- **输出处理不当（LLM10）** 和 **过度自主权（LLM03）** 往往会一起放大实际执行面的风险
- **向量与嵌入弱点（LLM09）** 可能让错误或恶意上下文进入生成环节，并进一步放大 **错误信息（LLM07）** 的影响

实际的安全架构设计需要从这个全景视角出发，构建多层防御来割断这些风险链条。具体的防御策略将在 [第 4-7 章](../04_prompt_injection/README.md) 逐一讲述。

### 3.1.2 LLM01：提示注入

**为什么提示注入排在首位？**

提示注入是 LLM 应用的“根本性”威胁。不同于传统 Web 应用的 SQL 注入需要“发现可注入点”，LLM 在架构上根本不区分“指令”与“数据”——两者都是同一条 Token 流上的 Token，因此不存在参数化查询那样干净的等价物。2026 版把“输入”的范围显式铺开：它不必是人类可读的文本，不必直接来自用户，也不必在渲染出的界面里可见——检索到的内容、工具输出、图像、音频、视频、中间推理过程、持久化记忆，都是能改变模型行为的输入。一旦提示注入成功，攻击者获得了对模型执行流的控制权，进而可以：
- 泄露系统提示内容、检索到的私有文档或基础设施细节（导致 `LLM08:2026` 隐藏上下文暴露与 `LLM02:2026` 敏感信息泄露）
- 诱导模型调用它本就有权调用的工具，在具备 shell、文件系统或云 API 权限时升级为任意命令执行（导致 `LLM03:2026` 过度自主权）
- 操纵模型输出，产生带偏见的、有害的或攻击者指定的内容，让下游系统或用户据此行动

边界需要划清：本条关心的是**输入边界本身**；模型输出在被下游组件消费前的清洗与校验属于 `LLM10:2026` 输出处理不当。

新版还点明了三条放大后果的部署期性质。一是**上下文窗口池化**：系统提示、用户输入、检索文档、工具输出、会话历史与记忆被当作同一条 Token 流，其间没有被强制执行的信任边界。二是**记忆持久化**：一次写入长期记忆、检索增强生成（RAG）语料库或向量库的注入，会污染此后每一个读到它的会话。三是**智能体式执行**：当模型输出驱动工具调用时，影响面从对话界面扩展到工具能触及的一切，而工具输出又重新回到上下文窗口，形成链式甚至自我复制的效果。做威胁建模时，可以沿三条轴先拆解具体场景——投递面（直接输入、检索内容、工具输出、工具连接通道、持久化记忆）、传播行为（单次、多步杀伤链、经记忆或 RAG 跨会话、在智能体之间自我复制）、编码方式（明文、Base64 等混淆、不可见 Unicode、多模态或隐写、低资源语言），再决定套用哪些缓解措施。

**风险描述**：攻击者通过恶意指令影响模型执行路径，绕过系统规则。

**典型场景**：直接注入、间接注入（检索内容与工具返回）、多模态与隐写注入，以及写入跨会话记忆或 RAG 语料后被反复读取的持久化注入（语料本身被持久污染的部分归 `LLM05:2026`）。

**防护思路**

提示注入防护的核心思路是“分层隔离”——在架构上将“系统规则”和“用户数据”“外部内容”分离。来源标记、上下文隔离、工具调用前置校验都能降低提示注入的成功率，但不能提供可靠、不可绕过的边界。2026 版把这一点说得更直白：指令与数据不可区分、模型行为又具随机性，因此今天不存在可靠的预防机制，防御是**架构性**的而非**拦截性**的——要按“模型的指令边界终将被绕过”来设计周边系统，约束模型被允许做什么、它的输出被允许触及什么。Simon Willison 的“致命三要素”把这条判断变成一项上线前检查：一个智能体如果同时能访问私有数据、摄入不可信内容、并对外通信，就凑齐了高影响利用的条件，去掉其中任何一条即可破局。同时，对于从外部系统（如网页、文档、MCP 服务器）返回的内容，更应该建立特殊的检测与沙箱化处理，并且评测必须交给读过防御方案的自适应攻击者——有研究对 12 种近期防御做过测量，静态攻击成功率接近零，而自适应攻击下多数超过 90%。

**防护重点**
- 指令层与数据层分离：外部内容走结构上独立、带来源标注的通道传入，让模型能区分数据与指令；但这只在非自适应测试中降低成功率，知道标注方案的攻击者可以伪造它
- 全模态入口清洗：对文本、图像、音频、结构化数据分别过滤（图像做 OCR、音频做转写后再套文本过滤），并在每个摄入与渲染边界剥离标签块、变体选择符、零宽字符这类不可见 Unicode
- 权限预算与确定性中介：凭据与状态变更能力留在应用代码而非模型中，并以 Rule of Two（不可信输入、敏感数据、状态变更或对外通信三者最多取其二）为架构底线——注入终会成功，能限制后果的是模型之外的权限设计，其展开见 `LLM03:2026` 过度自主权

**落地提示**：这一类风险在工程上通常会落到输入边界隔离、来源标记、不可见字符剥离、工具调用前置校验与关键动作人工确认等控制点上；具体门控架构将在第四章展开，智能体场景下的权限预算与记忆写入治理见第七章。

### 3.1.3 LLM02：敏感信息泄露

**与 LLM01 的关系：从“破口”到“后果”**

如果说提示注入是攻击者的“破口”，那么敏感信息泄露就是最常见的“后果”。攻击者获得控制权后，首先想到的就是套出隐私数据、系统秘密或其他用户信息。与此同时，即使没有成功的注入攻击，模型在正常运行中也可能因为：
- 训练数据记忆泄露
- 上下文与日志处理不当
- 多租户隔离缺陷

而无意中向用户暴露敏感信息。因此，**敏感信息泄露防护是两层的**：一是通过提示注入防御减少被“套取”的风险，二是通过输出侧的脱敏和 DLP 措施防止“无意泄露”。

2026 版把“输出”的边界大幅推宽：除了最终答案，工具调用参数、推理轨迹、检索到的文档片段、多模态输出、日志与遥测、嵌入向量，以及外部可观测的推理属性（时延、Token 长度、对数概率、置信度、缓存命中行为）都是泄露面，都要按同一套分级与脱敏规则来对待。泄露相应地被归纳到四个阶段：训练期的记忆与抽取、推理期的上下文回显、流水线期（微调、蒸馏、合成数据生成、可观测性）向衍生产物的搬运，以及观测期——攻击者不接收任何内容，仅凭外部可测量的属性推断事实。跨模态是另一处扩展：视觉模型会从截图、通知和 PDF 元数据中 OCR 出凭据与 PII，而“文本渲染成图片、图片再 OCR 回文本”这类跨模态变换，可以绕过只覆盖单一模态的 DLP。

新版还点明了两类结构性成因。一是上游过度共享：未收敛的网盘权限、历史遗留的 ACL 和知识库把本不该开放的数据喂给了 RAG，模型只是“按设计”把它检索了出来，要修的是数据面而不是模型。二是持久化：数据一旦影响了权重、嵌入或适配器，即使删除源文件仍然可被抽取，这会直接冲击 GDPR 第 17 条与 CCPA §1798.105 的删除义务；开放权重的部署更不能指望限流，因为抽取、成员推断和反演都可以离线无限次地跑。至于模型不再只是应用内组件、而是能跨会话携带记忆并自行选择工具时被放大的那部分风险，归属智能体清单（见第七章）。

**风险描述**：模型输出或上下文处理过程泄露隐私、密钥、系统细节或跨租户数据。

**泄露路径**：训练记忆抽取、上下文回显、推理轨迹与日志误采集、嵌入向量反演，以及时延与 Token 长度一类的推理侧信道。

**防护思路**

敏感信息泄露防护需要“双向夹击”：一是在输入侧，通过脱敏和 PII 检测防止敏感数据被无意中送入 LLM；二是在输出侧，通过 DLP 和脱敏规则防止 LLM 的输出包含机密信息。在多租户场景下，还需要在存储、索引和日志层面进行严格的隔离，确保一个用户的信息不会“串”到另一个用户的上下文。关键是建立“最小信息原则”——只向 LLM 提供完成当前任务所需的最少敏感数据。两点工程细节值得单独强调：授权必须前置到检索，鉴权要落在索引查询内部而不是检索之后在应用层过滤，因为已经送进模型的片段撤不回来（分块级权限与多租户索引的具体做法见 `LLM09:2026`）；出站检测也不能只靠正则，跨语种、Base64 与 hex 编码会轻易穿过黑名单，需要配合 NER 与训练过的分类器。此外，可观测性平台默认就会完整记录提示、补全、检索片段和轨迹，接入 APM 之前必须先限制采集范围并做清洗。

**防护重点**
- 输入输出双向脱敏：清洁入站数据，审计出站内容，并把推理轨迹与工具调用参数当作一等输出来分级、脱敏
- 检索前授权与多租户隔离：把文档级、分块级鉴权下沉到索引查询内部，高敏感负载使用独立的租户索引，日志中的敏感内容加密存储并自动清理
- 敏感字段检测与侧信道收敛：自动识别 PII、密钥等字段并触发审计告警，同时在生产端点上收敛对数概率与置信度、对流式响应做随机填充与批量化

**落地提示**：这一类风险通常要求输入脱敏、输出脱敏、检索前授权、多租户隔离和日志最小留存等组合控制；嵌入向量的**反演机制**归 `LLM09:2026`（向量与嵌入弱点），而**定级归本条**——被导出或泄露的向量可被反演还原出明文，因此“只泄露了嵌入”的备份要按源文档级泄露对待、触发相应的通报评估；本条关注的正是训练与推理链路上的泄露及其带来的监管后果与删除义务，具体工程做法将在第九章展开。

### 3.1.4 LLM03：过度自主权

**权限失控的加速器**

前一条 LLM02 关心的是“信息被读走”，而 LLM03 关心的是“动作被做出”。它在 2026 版中从 2025 版的第 6 位升到第 3 位，首次进入前三——官方称这是本版清单上最具后果的一次移动，因为投票与真实事件记录在这里罕见地一致：损失正落在智能体部署上。原因不难理解：随着智能体（Agent）技术的普及，LLM 被赋予了越来越多的“能力”——调用外部 API、访问数据库、发送邮件、修改文件等（不同厂商把这类能力叫作工具、扩展、插件或技能）。这些能力本身无关安全，但问题在于：
- **权限矩阵爆炸**：100 个工具的排列组合可以产生极高的风险组合
- **人工审查失效**：无法逐一审查每个潜在的权限链
- **缺乏运行时约束**：给 LLM 的权限往往是静态的、“要么全有，要么全无”

官方把根因归结为三类：功能过度、权限过度、自主性过度。而触发它的既可能是幻觉或模型本身表现不佳、目标错位，也可能是直接或间接的提示注入——注入源除了恶意用户，还包括上一次被攻陷的工具调用，以及多智能体协作场景中一个已被控制的同伴智能体。

因此，**LLM03 的防护不仅需要权限设计的精细化（RBAC），更需要运行时的动态收敛**——在每个请求时刻，根据上下文和意图，动态地限制 LLM 当前可用的权限。这与传统应用的“连接时拿到所有权限”的设计思路完全不同。2026 版还特意划清了边界：对模型输入输出做净化并不是本条的根本控制手段，输入侧属于 `LLM01:2026`、输出侧属于 `LLM10:2026`，本条要管的是“这个动作到底该不该被执行”。在智能体形态下，它会具体表现为智能体清单里的 `ASI02` 工具滥用与利用、`ASI03` 身份与权限滥用，以及 `ASI08` 级联失效。

**风险描述**：智能体被授予过多权限后，可能执行越权调用、批量外发或破坏性操作。

**防护思路**

过度自主权问题根本上源于“给与”和“使用”的不对称——权限设计时是“长期、静态、宽泛的”，但执行时应该是“当前、动态、最小化的”。在 Agent 架构中，需要从多个维度进行权限约束：
1. 功能维度：定义每个 Agent 的能力范围（调用哪些工具），并尽量避开“执行任意 shell 命令”“抓取任意 URL”这类开放式工具，改用粒度更细、且为入参定义了严格 schema 并在使用前校验内容的专用工具
2. 参数维度：限制工具参数的有效范围（只能操作特定数据、用户或时间段）
3. 时间维度：使用短期令牌而非长期凭证，减少凭证泄露的影响
4. 行为维度：监控权限的使用情况，异常调用立即告警；同时为工具调用设定阈值与熔断，超过阈值即中止、限流或转人工复核

**防护重点**
- 最小权限与时效令牌：Agent 只获得完成当前任务所需的最小权限，使用过期时间短的临时令牌；在委托链和多智能体流程中，要把原始用户的身份与授权范围一路传递下去，而不是退化成调用方智能体或服务账号的权限
- 人工审核（HITL）审批：高危或异常的工具调用需要人工确认，而不是直接执行；2026 版进一步建议采用分级执行策略（审计、告警、阻断、升级），低后果或易回滚的动作可以自动放行，不可逆的动作才路由到人工
- 高风险工具硬性阻断策略：某些工具（如删除数据库、转账等）永不允许 Agent 直接调用，必须经过显式的人工授权；授权判定要用代码逻辑做完全仲裁（complete mediation），由工具、独立的前置策略决策点或下游系统来校验，而不是交给 LLM 自己判断

**落地提示**：这里更适合作为权限设计原则来理解：最小权限、短时授权、运行时收敛与人工确认，而不是在框架导读阶段先固化某一套实现细节。

### 3.1.5 LLM04：供应链风险

**风险链的“上游”威胁**

前面三条风险——提示注入、敏感信息泄露、过度自主权——主要体现为系统跑起来之后的运行时风险，而供应链风险来自更前面的阶段：在模型和应用还未上线时，污染就可能已经开始植入。供应链风险的特点是“影响面广、发现较晚”，因此组织需要把它纳入开发与部署链路的持续治理，而不是仅靠上线后的补救。

`LLM04:2026` 把攻击面从传统的代码与依赖扩展到了模型制品本身：第三方预训练模型、数据集、用 LoRA 等参数高效微调（PEFT）技术做出并共享的适配器都被纳入其中，而模型制品、来源证明（provenance）与格式转换、合并流水线是新版明确列为一等攻击面的三样；端侧部署的 LLM 进一步把设备制造过程、固件与操作系统漏洞、被重新打包的应用也拉进这条链路。与之相关的两条边界需要说明：

- 本条与 `LLM05:2026` 数据与模型投毒有重叠，区别在于本条只看这些风险的供应链侧面。
- 智能体特有的供应链风险（如 MCP 服务器与工具注册表）不在本清单，而由 OWASP Top 10 for Agentic Applications 的 ASI04 覆盖；MITRE ATLAS 则以 `AML.T0010` 收录对应的攻击技术。

**风险描述**：模型、适配器、数据集、依赖库、镜像、转换与部署平台任一环节被污染都可影响系统。

**典型场景**：把公共模型库上的模型只按 `Author/ModelName` 引用，原作者注销或转让账号后攻击者抢注同名路径，流水线随即拉到恶意模型。

**防护思路**

供应链安全的核心是“源头认证”和“全链路追踪”。在持续集成流水线中，从模型拉取、依赖下载到容器镜像构建，每一步都应该有校验机制；同时，应通过 SBOM 及其面向模型的扩展（AI BOM / ML-BOM）追踪组件的来源、版本、许可证和漏洞状态。新版还特别提醒：不要把恶意软件扫描器和“安全加载”开关当成保证——它们自身出过被分配 CVE 编号的绕过，而藏在计算图里的后门在 ONNX 这类公认安全的格式中同样能留存；量化则是一次可被利用的转换，权重可以被构造成全精度模型评测正常、量化后的制品却按攻击者意图行事。当发现供应链污染时，必须能快速识别受影响的下游应用并进行紧急响应。

**防护重点**
- 来源可追溯（签名/校验）：对模型、适配器与镜像做签名和哈希固定，并用不可变摘要而非 `latest` 这类可变引用来拉取；但签名只证明完整性与来源、不证明安全性，仍需配合行为评测与发布门禁
- 依赖锁定与漏洞扫描：在构建时锁定依赖版本，定期扫描已知漏洞（CVE），并在采纳 AI 编码助手建议的依赖前先确认该包真实存在且确为目标包，避免踩到被预先抢注的幻觉包名
- SBOM 与变更审计：为每个部署生成 SBOM，并扩展到覆盖模型、适配器与数据集的 AI BOM / ML-BOM，记录完整的变更链条便于事后追溯与合规审计

**落地提示**：工程落地时应关注签名校验、依赖锁定、漏洞扫描和供应链追溯能力，并把模型转换、合并服务以及自有 CI/CD 发布流水线当作高风险的“晋级点”重点监控——由自家发布设施构建并签名的制品，恰恰能通过下游的来源校验；但本章重点仍是理解风险边界，而非展开完整的 CI/CD 控制清单。

### 3.1.6 LLM05：数据与模型投毒

**“污染源头”的深层威胁**

如果说 `LLM04:2026` 关心的是外部组件的来源是否可信（第三方模型、数据集、依赖），那么本条关心的就是这些数据和模型工件被摄入之后如何被持久地污染——攻击者可能通过污染你自己的训练数据、微调数据或 RAG 知识库来长期改变系统行为。这种攻击的可怕之处在于：
- **潜伏性强**：植入的“后门”或偏差可能在数周甚至数月后才被发现
- **难以根治**：需要重新清洗数据和重新训练，成本极高
- **难以追溯**：如果数据来自众多外部贡献者或网络爬取，找到污染源头困难重重

2026 版把这条的范围从传统意义上的“训练数据”明确扩展到数据被摄入、转换、检索、复用的任何环节，涵盖预训练、微调、嵌入生成、RAG 与模型分发。随模型一起分发的非权重工件——聊天模板、分词器配置、LoRA/PEFT 适配器、量化产物，以及 pickle 之类的不安全序列化文件——同样可能在加载时执行恶意代码或改写模型行为，而这类后门可能在触发条件出现之前都不改变模型的正常表现，从而让模型有机会成为一个“潜伏特工”。官方还援引研究指出，仅 250 份投毒文档就足以影响 600M 到 13B 参数区间的模型，且与数据集规模无关，因此“语料足够大就能稀释污染”的直觉并不成立。

新版同时划清了几条边界：推理时经检索内容送达的指令属于 `LLM01:2026` 提示注入，利用嵌入几何结构做的攻击属于 `LLM09:2026` 向量与嵌入弱点，本条覆盖的是对持久化数据或模型行为的**持久性破坏**；而工具集成、跨会话记忆与 RLHF 反馈回路上的投毒，官方把深入讨论交给了《OWASP Top 10 for Agentic Applications》。

因此，**数据投毒防护的关键是事前验证和事中监控**，而不是事后救补。

**风险描述**：攻击者污染训练、微调、嵌入或检索数据乃至模型工件，诱导系统长期偏离预期行为。

**投毒环节**：预训练语料、微调数据集、嵌入与向量库、迁移学习复用的上游模型，以及持续学习与自动再训练管线，都是可下手的位置。

**防护思路**

数据投毒防护的难点在于“隐蔽性”——有害样本往往看起来无害，需要通过统计异常检测或行为基线比对来识别。因此，防护策略应该分为“事前”和“事中”两层：事前通过严格的数据来源审核和清洗减少污染概率，事中通过模型行为监控和 A/B 对比发现变异。一旦发现投毒，需要能快速回滚到已知安全的模型版本。自动再训练和用户反馈回路要额外当心：攻击者只需普通的界面访问权限，就能靠持续投喂让模型缓慢漂移，因此这类回路必须限速、校验并保留人工审核。

**防护重点**
- 数据摄入白名单与分级审核：建立受信任的数据来源清单，对新增数据进行内容和来源审核，并对检索内容设置信任边界与来源评分
- 模型工件血缘与加载前校验：把聊天模板、分词器配置、适配器与量化产物当作与代码同等重要的安全对象，加载前完成哈希与差异校验（签名与 BOM 的建立方式见 `LLM04:2026`），并记录它们与训练数据集之间的血缘
- 模型版本基线与行为回归测试：维护模型与数据集的历史版本（如用 DVC），定期运行回归测试套件与触发词探测，验证输出分布稳定并支持快速回滚；不要假设安全对齐能清除后门，每轮对齐之后都要重新探测

**落地提示**：这类风险的核心是“数据来源可信 + 模型工件可验证 + 行为回归可复核”；更细的训练与数据治理控制将在第二章和第八章展开。

### 3.1.7 LLM06：无边界消耗

**“肉体”上的拒绝服务**

如果说 `LLM05:2026` 盯的是模型的训练数据与权重，那么本条盯的是模型运行时的算力与预算——通过不受控的推理让服务退化、成本失控，或者被反复问答“抄走”模型本身。2026 版把这条风险的本质概括为**成本不对称**：攻击者只需付出微不足道的代价，就能触发极其昂贵的计算，手段可以是精心构造的提示、被窃取的凭据，或被操纵的工作流。官方在本版列出的典型形态包括：
- **变长输入洪水与输出爆炸**：超长且长度不一的输入抬高处理成本；输出侧则可能来自微调投毒——一个恶意训练样本破坏模型的结束符行为，使其此后每次请求都把输出顶到最大长度
- **大上下文滥用**：许多 API 会直接拒绝超出上下文窗口的输入，因此真正持久的风险来自那些贴着上限、却始终不越界的请求，以及会话内的上下文累积和应用侧的重新分块
- **推理循环与思考 Token 耗尽**：短小、看起来人畜无害的提示，把扩展思考模型拖入漫长甚至不终止的推理循环，耗尽思考 Token 预算，而输入长度过滤对此完全无效
- **为过度消耗资源而优化的对抗输入**：海绵样本与对抗性视觉扰动，用梯度或非梯度方法专门优化出“最贵”的输入，这与单纯让模型去做一件费算力的事不是一回事
- **钱包拒绝服务（Denial of Wallet，DoW）**：用大量合法但按量计费的操作，把成本压力转嫁给服务方

清单还覆盖了多模态输入输出、模型抽取与蒸馏窃取、Agent 与工具交互泛洪，以及推理基础设施本身被利用。多模态模型会把图像、音频、视频展开成大量 Token，同一次请求的开销可以远高于纯文本，具体倍数取决于模型、供应商、分辨率、媒体时长和预处理管线。模型抽取则是用构造过的查询批量收集输出，复现出部分模型或微调出一个功能等价物，暴露 logits 与对数概率会显著加速这一过程；而通过计时或共享基础设施观测来侧信道提取权重与架构，官方明确划归 `LLM02:2026` 敏感信息泄露。

与传统 DDoS 相比，这类请求往往更像“合法调用”。2026 版进一步指出，**仅靠传统的请求速率限制已经不够**：扩展思考与推理模型带来了庞大且约束不足的输出预算，多模态大幅推高单次请求成本，智能体架构与工具调用协议（如 MCP）会把一次请求放大成级联的下游操作，共享推理基础设施又引入了新的供应链攻击面。有效的防御需要面向 Token 的成本控制、硬性支出上限、智能体级熔断器，以及持续的成本归因监控。

**风险描述**：攻击者通过高并发、长上下文、高复杂度请求或递归工具调用，消耗预算与算力，乃至复制模型本身。

**典型场景**：攻击者或普通用户维持一个长开的智能体会话并不断注入内容，使每次推理都重新处理全部累积上下文，单轮成本从第一轮的约 0.001 美元涨到第 100 轮的约 0.50 美元，而没有任何单个请求触发速率限制。

**防护思路**

无边界消耗的防护需要在多个维度设置“熔断”和“配额”：
- 在用户维度，按 API Key、用户、团队和云账号设置不可覆盖的预算上限——它必须是超限即停止推理的执行机制，而不是让快速累积的负载轻易跑赢的告警阈值
- 在请求维度，限制单个请求的 Token 数、推理步数、工具调用次数，并用预检 Token 估算在推理开始前就拒绝请求
- 在全局维度，做动态资源分配与优雅降级，让系统在高负载下保留部分功能而不是彻底失效

关键是“主动设限而非被动超支”——上限必须是超限即停止推理的执行点；持续的成本归因监控只能让问题被更早看见，代替不了这个执行点。

**防护重点**
- 速率限制与 Token 成本控制：从每秒请求数走向每分钟、每天的 Token 配额与单请求预估成本，并让支出上限体现不同模态与工具协议之间的成本差异
- 智能体熔断与工具行为基线：对每次 Agent 执行强制步数、递归深度、时限与单次运行成本上限，用状态哈希识别递归循环，并为工具的正常 Token 消耗建立基线以发现异常会话
- 推理基础设施加固：及时更新 vLLM、TensorRT-LLM、SGLang、Triton、Ollama 等服务框架，禁用不安全的反序列化，限制特殊 Token 透传，并对所有推理端点强制认证

**落地提示**：这一风险在工程上落到三个控制点——网关侧的速率与 Token 配额、账单侧的硬性支出上限、以及 Agent 运行时的熔断器，本书第七章讨论智能体与工具调用安全时会继续展开；本章的重点则是帮助读者先识别“消耗本身也是攻击面”。

### 3.1.8 LLM07：错误信息

**“有理有据”的谎言**

前面的 LLM05 与 LLM06 讲的是攻击者对系统的直接施压——投毒或耗尽资源，而 LLM07 的危害往往不需要攻击者在场：模型输出虚假、不完整、缺乏依据或具有误导性的信息，而这些信息看上去足够可信，足以左右一次人类决策、一条自动化流程或一次智能体动作。真正的风险不在于模型说错了，而在于错误被信任、被据以行动。这对金融建议、医疗信息、法律意见等高敏场景构成直接威胁。关键是：
- **虚假内容可能被用户全盘接受**，因为 LLM 说得条理清晰、甚至“引经据典”；流畅、自信、结构工整的输出天然被当成权威
- **成因不止幻觉一种**：上下文不完整或过时、接地不足、提示歧义、被污染的数据、误导性摘要、未经校验的工具输出都会导致错误信息，攻击者也可以刻意诱发
- **跨链接损伤**：一个错的 RAG 检索结果会污染后续的推理，在多智能体编排中还会跨智能体扩散

2026 版把这一条从“模型说错话”提升为系统级失效。在今天的系统里，模型输出会驱动工具调用、生成代码、推断系统状态、批准动作并在多个智能体之间传递，因此一次错误信息可以直接演变成资金损失、安全事件、人身安全风险或业务中断。在智能体架构中，它通常表现为错误的状态、推理或证据被下游组件照单全收：智能体误判某个前置条件已经满足而触发后续动作，检索智能体谎报客户“已完成身份核验”而下游支付智能体据此放款，或者智能体报告夜间数据库备份已完成、直到真正需要恢复时才发现备份从未运行。新版还特别点名了伪造或错误归属的“证据”——被捏造、被篡改的内容被当作权威依据呈现。更麻烦的是，这种过度信任常常不是用户的一时疏忽，而是被固化进了系统设计本身。

新版也顺带划清了与相邻条目的边界：不安全生成代码的执行与处理属于 `LLM10:2026` 输出处理不当，把模型幻觉出来的包名抢先注册成真实软件包这一供应链手法属于 `LLM04:2026` 供应链风险；若根因是提示注入、投毒或供应链失陷，应回到对应条目讨论。本条只聚焦最终的失效形态——一个虚假的表述驱动了有害的决策或动作。

防护 LLM07 的核心思路仍然是 **“验证而非信任”**——通过引用溯源、事实性评测、高敏场景的人工复核等手段来补偿 LLM 本身的缺陷。

**风险描述**：模型输出错误但看似可信的信息，被人或下游组件当作事实采纳，进而驱动有害的决策或动作。

**防护思路**

错误信息风险无法仅靠架构设计彻底消除。防护重点更接近“检测和补偿”：
- 行动前先给结论找依据：要求输出落在权威且时效的来源上（例如用检索增强把结论绑定到可查证的出处），依据要在动作发生之前建立，而不是事后交给用户核对
- 把生成与执行分开，先核验声明再动作，并在工具调用前逐项检查参数、授权、前置条件与当前状态
- 在金融、医疗、法律等高敏场景，部署事实性验证和人工复核，对高影响动作引入审批流与系统校验
- 收敛影响半径：最小权限、沙箱与限流，让一次错误信息不至于扩散成一次事故
- 校准人与系统的信任：明确区分已验证的事实与未经证实的假设，记录声明、证据与结果，并定期用误导性场景做对抗性评测

**防护重点**
- 引用来源与事实核验：强制 LLM 附加检索来源链接，对于关键事实进行自动事实性检验（如金融数据对比、医学文献查证），并以接地性与一致性等验证信号为准，而不是只看模型自报的置信度
- 高风险域强制人工审核（HITL）：医疗诊断、法律意见、投资建议等高风险内容必须经过人工审核，高影响动作还应有运行时校验与审批环节
- 不确定性提示与遗漏防护：在高风险场景中提示不确定性并建立升级路径，同时用带必填字段的结构化输出，防止关键约束、例外、时间戳被悄悄省略

**落地提示**：面对错误信息，框架层最重要的是建立“验证而非信任”的思维；具体的事实核验、来源约束和人工复核机制更适合在后续输入输出防护章节展开，而跨智能体的状态与证据信任问题则在第七章的智能体安全中继续讨论。

### 3.1.9 LLM08：隐藏上下文暴露

**破口背后的秘密**

上一条 LLM07 关心的是模型说出来的内容能不能被信任，本条关心的是模型本来不打算说出来的那部分内容能不能被套走。它由 2025 版的“系统提示泄露”改名并扩范围而来：系统提示只是隐藏上下文的一种，真正的失效是“本不该被读到的信息被读到”。它常与提示注入配合出现：注入负责改写系统行为，本条负责先探明系统设计——被披露的规则、工具与格式，正是构造注入负载的素材。一旦隐藏上下文暴露过多内部细节，攻击者就更容易了解：
- 系统的约束与策略（知道了“防线在哪”）
- 模型的工具列表、函数 schema 与权限（知道了“能做什么”）
- 可能的内部流程与数据流（知道了“怎么做”）

官方把“隐藏上下文”界定为应用组装进模型上下文窗口、却不打算让终端用户看见的那部分材料：系统提示、开发者指令、从 RAG 知识库、配置存储或用户画像服务取回的策略文本、应用暴露给模型的工具与函数 schema，以及其它规则和指令。它们的共同点是不面向终端用户，却对模型可见——因此也就可能被抽取、被推断、被重建。

因此，**LLM08 的核心不是“把系统提示当作秘密藏起来”，而是不要把机密、鉴权逻辑和安全边界委托给隐藏上下文本身**。工程上应当直接假设隐藏上下文是可被发现的、其中任何内容都不应被视为秘密，并让“它被披露”这件事本身几乎没有直接安全影响。危害程度取决于里面放了什么、以及应用有多依赖它保密：从信息级（无机密、无安全相关逻辑、不依赖其保密性），到中危（内部规则、过滤标准、角色描述或流程逻辑，对攻击者有实质帮助但不决定关键判断），到高危（内嵌凭据或令牌，或把授权与内容策略建立在上下文保密之上），直到严重（披露可链式导致远程代码执行、大范围数据外泄或关联系统的权限提升）。

它自身有风险，也会放大相邻条目的风险：被披露的规则与逻辑让提示注入更有针对性，内嵌的凭据直接构成敏感信息泄露（`LLM02:2026`），暴露的工具权限与 schema 扩大了过度自主权（`LLM03:2026`）的攻击面，泄露的输出格式规则则便于制造输出处理不当（`LLM10:2026`）。反过来，受监管的用户数据或训练数据的泄露归 `LLM02:2026`；持久记忆、智能体间通道、工具配置持久化、多步骤智能体沦陷这类放大形态归《OWASP Top 10 for Agentic Applications》；服务端日志泄露、前端产物被翻查、基础设施层旁路等通用应用安全问题也不在本条范围内。

**风险描述**：攻击者通过抽取、推断或重建，拿到系统提示、策略文本、工具 schema 等本不面向用户的隐藏上下文，从而实质提升攻击能力。

**典型场景**：敏感功能与工具 schema 外泄、内部决策逻辑外泄、安全与拒答机制被逆向、权限与角色信息被披露（例如内部 MCP 服务器给出的工具描述写明某项操作需要开发者角色）、输出结构与格式规则被披露。

**防护思路**

隐藏上下文暴露的根本问题是“机密信息、授权边界或控制逻辑被塞进了上下文”。防护的首要原则是“机密永不入上下文”——密钥、连接串、令牌等应外置到模型不直接接触的系统，并尽量不让模型经手敏感数据本身。其次，关键行为要靠模型之外的确定性系统与护栏兜底：有害内容的检测与拦截应由外部防护完成，而不是写一条指令请模型自觉；针对性的微调或继续训练也许能降低泄露概率，但不提供一致保证，还可能带来其它意料之外的后果。第三，权限分离与授权边界检查必须以确定性、可审计的方式落在 LLM 之外，任务需要不同访问级别时按授权上下文拆开，各自只授予所需权限。官方给出的缓解方向就是上面三条。工程上还值得再加一条本书的建议：对攻击者常见的“提示提取类”请求做意图检测与输出过滤，并通过红队测试和持续监控验证系统的“抗提取能力”。

**防护重点**
- 隐藏上下文中不存放机密：API 密钥、数据库连接串、用户令牌等一律外置到密钥管理系统，并假设模型能看到的一切用户也能看到
- 安全决策不依赖上下文保密：授权、权限分离、内容过滤交给 LLM 之外确定性且可审计的组件，系统提示只保留必要的行为约束；不要指望靠微调兜底，针对性微调也许能降低泄露概率，但不提供一致保证
- 用测试集持续回归“抗提取能力”：识别常见的提取提示词（如 `repeat your instructions`、`what are your rules`），结合输出过滤进行阻断，并把红队用例纳入 CI/CD 流水线

**落地提示**：官方的三条缓解措施可以概括为“机密不入上下文 + 确定性护栏 + 授权独立于 LLM”；本书再补一条工程实践——提取意图检测与抗提取测试。具体方法可放到后续防御章节讨论。

### 3.1.10 LLM09：向量与嵌入弱点

**RAG 时代的新老攻击融合**

如果说 `LLM08:2026` 关心的是本该留在视线之外的隐藏上下文被套了出来，那么本条关心的是决定“模型能看到什么”的那套检索机制本身被做了手脚。随着 RAG 的广泛应用，整个架构从“单纯的 LLM”变成了“LLM + 向量库 + 检索器”。这引入了一个全新的攻击面：攻击者可以在 RAG 链路的多个环节进行污染或操纵。特别是：
- **向量数据库的访问控制薄弱**：相似度检索往往先在全量索引上跑完，权限过滤才在应用层补上，用户 A 可能检索到用户 B 的私密数据；即便每份文档都打了正确的租户标签、每次调用都做了鉴权，攻击者仍能用探针查询，从命中条数、分数分布和响应时延推断出别的租户有哪些数据、大致谈的是什么
- **检索期投毒**：攻击者把内容做得嵌入落点恰好贴近某条目标查询，用户一提问，这份内容就作为可信上下文送进模型；MITRE ATLAS 把这一类归为 `AML.T0070`（RAG Poisoning）
- **检索排名操纵**：通过精心设计，让恶意内容排名靠前，被模型优先“吸取”

2026 版把这条的边界划得比过去清楚得多。首先是范围更宽：RAG 只是最常见的形态，向量化的智能体记忆、语义缓存与去重流水线用的是同一套机器，只要相似度检索挡在数据源与提示之间，嵌入层就属于应用的信任边界。其次是与相邻条目的切分：经由检索内容实施的间接提示注入归 `LLM01:2026`，嵌入模型在训练期被投毒归 `LLM05:2026`，向量库组件的序列化缺陷归 `LLM04:2026`，不依赖嵌入几何的智能体记忆攻击则归智能体清单的 `ASI06`（记忆与上下文投毒，见第七章）；留在本条里的，是那些必须借助嵌入层才能成立的攻击——它们利用的是嵌入空间的几何与相似度检索的机制，而不是模型的指令遵循行为，很多攻击即便检索到的内容里一句恶意指令都没有，也照样成立。官方给了一个好记的分法：投毒让系统答错，反演让系统泄密，干扰让系统闭嘴，权限失效让系统不分对象。

这一版也把几类过去容易被忽略的形态摆到了台面上。嵌入反演已经不是学术玩具：零样本方法无需针对特定编码器训练，在跨域和黑盒条件下依旧有效，连存储时掺入的差分隐私噪声也挡不住，因此向量库备份、外发给第三方的嵌入、以及因云存储配置错误而暴露的嵌入，都应当按源文档泄露来定级，“只泄露了嵌入”不是安全港。检索干扰则是打在检索层的可用性攻击——一份不含任何恶意指令的“阻断文档”，只要能被特定问题检索到，就足以让模型拒答或声称自己没有资料。语义缓存和去重靠一个余弦相似度阈值判定“两段内容是同一份”，攻击者把内容做成刚好卡在阈值两侧，就能污染缓存条目、绕过去重，或者让正常的新内容被当成重复默默丢掉。跨模态编码器（如 CLIP、ColPali）把图像、音频、代码和文本映射进同一个向量空间，一张在人看来平平无奇的图片就足以贴近某条敏感文本查询而被检索出来，基于文本的内容扫描抓不到它，因为载荷根本不是文本。最后，如果应用把原始相似度分数直接返回给客户端，索引本身就成了成员推断的预言机——攻击者不需要看到内容，只要知道某份病历、某份法律文书在不在库里，信息就已经泄露了。

因此，**RAG 安全不是“拉个向量库就完事”，而需要从“文档摄入→嵌入→索引→检索→重排”全链路进行加固**。

**风险描述**：嵌入、索引、检索与重排链路被操纵或被反向利用，导致错误或恶意上下文进入生成环节，也可能让已存储的嵌入反过来泄露源数据。

**典型场景**：多租户 SaaS 共用一个向量索引、只在应用层做租户过滤，租户 A 靠一批探针查询就拼出了租户 B 的数据轮廓。

**防护思路**

RAG 系统的安全性取决于其最薄弱的环节。从文档上传到最终生成的整条链路都需要加固：
- 文档摄入阶段需要内容归一化、内容审核和注入检测，防止恶意文档植入
- 嵌入和索引阶段需要确保数据的机密性和完整性，混合信任级别的内容（外部网页、内部机密文档、合作方数据）应当分索引隔离，而不是靠共享索引上的分类标签
- 检索阶段需要把租户与权限范围写进索引查询本身、并在服务端校验，客户端传来的范围只是建议而非控制
- 重排阶段需要评估检索结果的可信度，防止恶意内容排名靠前
- 存储与轮换阶段需要在源文档删除后按期删除对应嵌入并做对账审计；更换嵌入模型时整库重新嵌入，不要新旧向量混用

**防护重点**
- 向量库访问控制与加密：租户与权限范围写进索引查询本身并在服务端校验，权限粒度下沉到分块（一份大体公开的文档里可能夹着一段机密）；嵌入加密存储、密钥与应用层分开管理，备份按源文档的敏感级别对待
- 检索结果可信度评估：对检索到的文档进行相关性和可信度评分，低于阈值的结果不进入 LLM 上下文；不要把原始相似度分数返回给客户端，并对可能被当作预言机反复探测的接口限速
- 文档摄入阶段注入扫描：入库前的归一化与不可见字符剥离沿用 `LLM01:2026` 的入口清洗要求，本条额外要做的是入库前的内容检查，并为每条嵌入记录来源、入库时间、信任层级与流水线版本，以便整批作废和审计

**落地提示**：这里最关键的是“权限隔离 + 检索可信度 + 文档摄入审查”三条主线，再加一条应急预案上的改动——把“只泄露了嵌入”按源数据泄露处理，纳入 GDPR 第 33 条一类的通报评估，后续 RAG/Agent 章节会进一步工程化展开。

### 3.1.11 LLM10：输出处理不当

**从“LLM 控制权”到“系统破坏权”的桥梁**

前面九条追问的大多是“模型被喂了什么、被训练成了什么、被授予了多少权限”，而 LLM10 追问的是最后一步：模型已经开口之后，这段输出被谁、以什么身份消费。即使输出本身不含恶意，只要下游把它当作“代码”或“命令”执行，模型层面的控制权就会落地成现实的破坏。特别是在 Agent 和工具调用场景中，LLM 的输出直接变成了：
- 数据库查询语句（SQL 注入）
- 系统命令（命令执行）
- 文件路径（路径遍历）
- API 调用参数（二阶注入）
- 终端、日志与聊天界面里被直接渲染的富文本

这意味着 **LLM 的防御不能只关注“LLM 层”，还必须在下游系统建立强制的“参数化”和“白名单”执行方式**，这是传统 Web 应用安全的基本原则，在 LLM 时代更加重要。

2026 版把“下游”的边界又往渲染端推了一步。除服务端的执行面之外，官方明确把会解释控制字符的终端、日志查看器与 IDE 面板也算作下游接收点——模型输出里的 ANSI 转义序列可用于视觉欺骗、剪贴板劫持（如 OSC 52），甚至触发终端模拟器自身的已知漏洞；同样被明确纳入的还有会自动拉取外部资源的客户端渲染器：聊天界面自动渲染 Markdown 图片或链接预览时，控制了部分上下文的攻击者可以把会话数据藏进图片 URL 的主机名或查询串中带走。此外，把 LLM 生成的代码不经人工审核与安全测试就自动编译上线，也被列为本条的典型攻击场景。

**风险描述**：将 LLM 输出直接用于 SQL、Shell、模板渲染、API 参数或终端与聊天界面的渲染，触发传统安全漏洞。

**判定边界**：输入侧的校验与净化属于 `LLM01:2026` 提示注入，输出内容本身是否正确、是否误导属于 `LLM07:2026` 错误信息，本条只管输出在传给下游组件之前有没有被当作不可信数据处理。

**防护思路**

这是一个经典的“信任边界漏洞”——LLM 的输出被下游系统当作“代码”而非“数据”。防护这个风险的核心原则是传统 Web 安全中的参数化，即使 LLM 输出看起来“合理”，也不应该直接拼接成命令。对于会解释内容的渲染面，还要在写入前净化 ANSI 转义序列、BEL、OSC、退格与回车等控制字符（必须保留时改为可见编码），并默认关闭 Markdown 图片、链接预览与 iframe 的自动加载，确有需要时限制在显式的来源白名单内，或交由服务端代理拉取并剥掉携带数据的查询参数。至于这些高危操作本身该不该被执行、要不要人工授权，属于 `LLM03:2026` 过度自主权；本条只要求一件事：即便动作已获批准，其参数与内容仍须按不可信数据处理。

**防护重点**
- 输出永不直连执行面：所有 LLM 输出都经过参数化或与上下文匹配的编码，永不直接进入 SQL 引擎、Shell、模板渲染，也不直接落入会解释控制字符的终端、日志与 IDE 面板
- 参数化调用与 schema 校验：使用白名单限制可用的工具和参数范围，生成的参数必须通过 schema 验证
- 生成代码不自动上线，输出侧留监控：LLM 生成的代码在编译部署前须经人工审核与安全测试，不因“输出可信”就跳过校验；同时对输出建立日志与异常模式监控，Web 场景再用严格的内容安全策略（CSP）兜住生成内容引发的 XSS

**落地提示**：这一风险的关键不在“模型能不能生成危险内容”，而在“系统是否把输出当作命令直接执行、当作富文本直接渲染”；因此后续章节会重点展开参数化、白名单、渲染面净化与输出侧监控机制。

### 3.1.12 使用建议

OWASP LLM Top 10 最适合承担“风险目录”的角色：帮助团队快速识别自己是否暴露在这些典型风险之下。至于更细的 NIST 映射、Agent 风险强化和具体控制方案，放到后续章节按主题展开，会比在这一节一次讲完更清晰。

2026 版把一句话放在了全篇开头，也贯穿了十个条目：**不要试图造一个骗不倒的模型，而要把模型周围的系统建好，让模型被骗倒时——它一定会被骗倒——没有重要的东西会坏掉**。这句话恰好也是本书第 8 章纵深防御的出发点：十条风险里真正能靠“模型更聪明”解决的很少，绝大多数要靠边界、权限、参数化和审计来兜住。

对读者来说，当前更重要的是先建立三个判断：

- **它适合做什么**：用来盘点应用层暴露面、设计安全评审清单、建立测试与红队场景。
- **它不直接替代什么**：它不是完整的治理框架，也不是逐项可直接复制的实施手册。
- **它到哪里为止**：模型是应用里的一个组件时，风险在本清单；模型开始自己调用工具、跨会话携带记忆、在下游引发后果时，要换用[第七章](../07_agent_rag_security/README.md)对照的 Agentic Top 10。
