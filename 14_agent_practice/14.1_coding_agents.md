## 14.1 编码智能体安全

编码智能体是目前部署最广、权限最大的一类智能体。它读取仓库里的任何文件，在开发者的机器或持续集成环境里执行命令，产出的代码还会进入下游的软件供应链。本节讨论这类智能体特有的攻击面：仓库内容、配置文件、生成的代码、智能体自身的分发渠道、持续集成环境，以及它被攻击者当作工具使用的情形。

### 14.1.1 为什么编码智能体风险最高

用 13.1 节的 Rule of Two 来衡量，编码智能体在默认配置下三项性质全部具备，而且每一项都处于最强的形态：

| 性质 | 在编码智能体上的表现 |
|------|----------------------|
| 不可信输入 | 第三方依赖的源码与文档、克隆来的仓库、Issue 与 PR 的内容、网页搜索结果、测试与构建的输出日志 |
| 敏感访问 | 开发者主目录下的云凭据与 SSH 密钥、环境变量中的令牌、代码托管平台的登录态、可达的内网服务 |
| 对外动作 | 任意命令执行、网络访问、提交与推送代码、发布软件包 |

此外它还有一个其他智能体没有的放大因素：**产出物本身会被执行**。聊天助手的错误输出需要人去照做才会造成后果，编码智能体写下的代码则会被编译、测试、合并和部署。一次成功的注入不仅影响当前会话，还可以把后门写进代码库，随发布流程抵达所有用户。

### 14.1.2 仓库即攻击面

对编码智能体来说，仓库里的每一个文件都是提示的一部分。攻击者不需要接触开发者，只需要让恶意内容出现在智能体会读到的位置。

**规则文件后门。** 编码智能体普遍支持在仓库中放置规则文件，用来说明项目约定和编码风格，智能体会把它当作高优先级的指令加载。Pillar Security 披露的 [Rules File Backdoor](https://www.pillar.security/blog/new-vulnerability-in-github-copilot-and-cursor-how-hackers-can-weaponize-code-agents)（附录 C-121）利用了这一点：在规则文件里用零宽连接符、双向文本控制符等不可见 Unicode 字符藏入指令，人工审查时看不到，模型却能完整读到。演示中，被污染的规则文件让智能体在生成的页面里悄悄加入指向攻击者服务器的脚本，并且指示它**不要在回复中提及这一改动**，因此聊天窗口里也不留痕迹。该攻击在 Cursor 和 GitHub Copilot 上均可复现。规则文件之所以危险，是因为它们常被当作无害的配置在团队和开源社区间流传，很少有人像审查代码那样审查它们。

**其他注入位置。** 同样的思路适用于智能体会读取的一切内容：

- **Issue、PR 描述与评论**：公开仓库上任何人都能提交，13.1.4 的 GitHub MCP 事件与 4.4.8 的 Clinejection 都由此入手。
- **依赖包的文档与源码**：智能体为了弄清一个库的用法会去读它的 README 和实现，被投毒的依赖包可以在其中夹带指令。
- **代码注释与字符串**：对人来说是数据，对读代码的模型来说是文本。
- **命令输出**：测试失败信息、构建日志、报错文本会回到上下文中，攻击者控制的测试用例或依赖可以在输出里写入指令。
- **MCP 配置文件**：仓库自带的 MCP 配置可以引入一个由攻击者控制的服务，或者在已获信任后被悄悄修改（1.2 节表中 Cursor 的两个 CVE 即属此类）。

防御上，除了 13.2 与 13.3 的通用手段，针对仓库内容有三条具体做法：对规则与配置文件做不可见字符扫描并纳入代码评审；在打开不熟悉的仓库时，先以不加载仓库内配置、不执行命令的受限模式查看；把“智能体读取了哪些文件”记入审计，以便事后追溯注入来源。

### 14.1.3 配置文件与自我修改

编码智能体的行为由一组配置文件决定：权限规则、钩子、MCP 服务列表、技能与自定义命令。这些文件带来两类风险。

**第一类是仓库携带配置。** 如果仓库内的配置文件能够放宽权限、注册钩子或添加 MCP 服务，那么克隆并打开一个恶意仓库，就等于让攻击者替你配置了智能体。钩子和本地 MCP 服务通常以用户的完整权限在沙箱之外运行（13.3.5），因此这相当于一条代码执行路径。应对方式是分层：项目级配置只能在用户级或组织级策略允许的范围内收紧，不能放宽；首次加载某个仓库的配置、或者配置发生变化时，必须经用户明确确认，并展示将要执行的完整命令。

这条路径在 2026 年被 Check Point Research 以三项漏洞（其中两项获得 CVE 编号）的形式证实（附录 C-140、C-141）。研究者发现，Claude Code 的项目级设置文件就放在仓库里，任何有提交权限的人都能修改，而其中的三种机制都可以被滥用：

- **钩子**。钩子本是为了给智能体行为加上确定性控制，例如每次编辑后自动格式化。但它定义在仓库控制的设置文件里，于是仓库可以让一条 Shell 命令在协作者的机器上执行。这一项发生在用户接受信任对话框之后，问题在于对话框没有就“将要执行仓库定义的命令”给出明确警示和单独确认。
- **MCP 自动批准**。设置文件中有允许自动启用项目内全部 MCP 服务的选项。研究者据此绕过了用户确认：命令在启动工具的瞬间就执行了，早于用户读完信任对话框（CVE-2025-59536，启动信任对话框实现缺陷导致的代码注入，已在 1.0.111 版本修复）。
- **环境变量**。设置文件可以改写接口基础地址。恶意仓库把它指向攻击者的服务器后，工具在显示信任提示之前就发出了带有 API 密钥的请求（CVE-2026-21852，已在 2.0.65 版本修复）。

三者的共同点是：**用户所做的只是克隆并打开一个仓库**。后两项的漏洞出在“信任确认”与“配置生效”的先后顺序上——配置在用户表态之前就已经起作用；钩子一项则是确认本身不充分。厂商的修复与此对应：强化信任对话框中关于钩子的警示，确保 MCP 服务在用户批准前不会启动，并把网络请求推迟到信任确认之后。Windsurf 的 CVE-2026-30615 展示了同一问题的另一个入口：智能体处理攻击者控制的网页内容时被注入，进而改写本地 MCP 配置、自动注册一个恶意的本地服务，无需用户进一步操作即可执行任意命令（附录 C-145）。

**第二类是智能体修改自己的配置。** 被注入的智能体如果能写入自己的配置文件，就可以给自己添加允许规则、注册一个下次启动时执行的钩子，或者改写 Shell 启动文件，从而把一次性的注入变成持久的控制。这正是 13.3.3 强调把这类路径列为禁止写入的原因。需要保护的不只是智能体自己的设置目录，还包括 `.git` 下的钩子与配置、编辑器配置目录、Shell 启动文件——所有“之后会被某个程序自动执行”的位置。

**关于跳过确认的模式。** 多数编码智能体提供不再逐条确认的运行模式，以支持长时间自主运行。这类模式本身不是问题，问题在于在没有其他边界的环境里使用它：在开发者本机上、带着全部凭据、不开沙箱地跳过确认，等于把 13.1 节的三项性质全部无监督地交了出去。正确的做法是把自主性与隔离绑定——只有在沙箱或一次性环境里，且凭据已被移出时，才启用跳过确认的模式。

### 14.1.4 生成代码带来的供应链风险

即使没有任何攻击者，模型生成的代码也会引入一类新的供应链风险：**幻觉出不存在的软件包**。

一项针对 16 个代码生成模型、覆盖 Python 与 JavaScript 的[大规模研究](https://arxiv.org/abs/2406.10279)（附录 C-122）生成了 57.6 万份代码样本，发现商业模型平均至少有 5.2% 的推荐包并不存在，开源模型平均为 21.7%，去重后共出现 205,474 个不同的虚构包名。论文同时发现这些虚构包名往往会在多次生成中持续重复出现，于是攻击者可以预先收集这些名字，抢先在公共包仓库中注册同名的恶意包。此后任何开发者或智能体照着模型的建议执行安装命令，都会把恶意包装进自己的环境。这种做法被称为幻觉包抢注（slopsquatting），与 12.2.2 的技能抢注原理相同，只是待抢注的名字由模型提供。

对会自行执行安装命令的智能体，这一风险不再需要人来“照做”。缓解措施包括：

- **安装前校验**：新增依赖必须存在于组织认可的清单或内部镜像中；对首次出现的包，检查其发布时间、下载量与维护者历史，新近注册且与知名包名字相近的应拦截。
- **锁定文件与完整性校验**：依赖变更必须体现在锁定文件的差异中并经过评审，安装时校验哈希。
- **禁用安装脚本**：在沙箱内安装依赖时默认不执行安装钩子，把“下载一个包”与“执行这个包里的代码”分开。
- **网络出口限定到包管理源**：配合 13.3.3 的代理白名单，使安装只能访问受控的镜像。

除了虚构依赖，生成的代码本身也可能含有漏洞或被注入后门，因此对智能体提交的变更，评审标准不应低于对人类贡献者的要求；对依赖声明、构建脚本、持续集成配置和权限相关代码的修改应强制人工评审。

### 14.1.5 智能体自身的分发渠道

编码智能体及其扩展是通过软件供应链分发的软件，同样会被投毒。

2025 年 7 月，Amazon Q Developer 的 Visual Studio Code 扩展 1.84.0 版本被发现含有恶意代码（附录 C-110，CVE-2025-8217）。根据 AWS 的安全公告，其构建配置中使用了一个权限范围不当的 GitHub 令牌，攻击者借此向扩展的开源仓库提交了恶意代码，这段代码随后被自动纳入正式发布。按 CVE 记录的描述，被植入的代码意在调用 Q Developer 的命令行工具；由于其中存在语法错误，它未能成功执行。AWS 撤销了凭据、移除了恶意代码并发布了 1.85.0 版本，同时要求所有 1.84.0 的安装都应停止使用。

这起事件没有造成实际损害，但它展示了一条值得警惕的路径：**攻击者不必注入某一次会话，而是把恶意代码植入智能体的发行包，通过官方渠道分发给所有用户**。结合 4.4.8 的 Clinejection（通过注入 Issue 分流机器人最终污染发布流水线），可以看到编码智能体的供应链存在一个闭环——智能体参与构建和发布自己，攻击者攻陷其中一环就可能影响全部用户。

防御要点与一般的软件供应链安全一致（8.6 节），针对智能体需要额外强调三点：构建和发布流水线使用的令牌必须最小化范围；智能体的系统提示、内置规则等“指令类资产”应与代码一样受评审和签名保护；企业应固定扩展与命令行工具的版本，经过验证后再升级，而不是自动跟随最新版。

### 14.1.6 持续集成环境中的智能体

把编码智能体接入持续集成，用于分流 Issue、评审 PR 或自动修复，是提示注入后果最严重的部署方式之一：触发条件由外部人员控制，运行环境带有仓库写权限和发布凭据，而且无人值守。

安全地这样做需要满足以下条件：

- **由不可信事件触发的任务不得持有任何写权限或密钥**。来自外部贡献者的 Issue、评论和复刻仓库的 PR 都是不可信输入。处理它们的智能体应运行在只读令牌下，输出限定为评论或标签这类影响有限的动作。
- **读与写分成两个任务**。需要写操作时，由读取不可信内容的任务产出结构化结果，再由另一个不读原始内容、持有写权限的任务执行，中间经过确定性校验（13.2.2 的模式）。
- **不与发布流水线共享缓存和运行环境**。Clinejection 的关键一步是通过缓存投毒从低权限工作流横向进入带发布凭据的工作流。
- **限制可用工具**。分流和评审任务不需要 Shell；能用固定的动作集合完成的，就不提供通用命令执行。
- **输出也要过滤**。智能体写回的评论会被渲染并被其他自动化读取，应防止它在其中输出密钥或可被下游解释为指令的内容。

### 14.1.7 被用作攻击工具的编码智能体

前面讨论的都是智能体作为受害者的情形。同样的能力也可以被攻击者直接使用。

2025 年 11 月，Anthropic 披露了其认定的首例由 AI 编排的网络间谍行动（附录 C-114）。按其报告，一个被高度确信为国家支持的组织在 2025 年 9 月中旬操纵 Claude Code，对约三十个全球目标发起渗透，目标包括大型科技公司、金融机构、化工企业和政府机构，其中少数获得成功。报告中的几个细节对防御方有直接意义：

- **绕过防护的方式是任务拆解与角色伪装**。攻击者把攻击拆成一个个看似无害的小任务，使模型在不了解完整意图的情况下逐一执行；同时声称模型是一家正规安全公司的员工，正在进行防御性测试。这说明仅在单次请求层面判断意图是不够的，需要跨会话、跨任务地检测行为模式。
- **人工介入很少**。整个行动的 80% 至 90% 由 AI 完成，每次行动中人只在约四到六个关键决策点介入。高峰期 AI 发出数千个请求，常常每秒多个，这是人工操作无法达到的速度。
- **模型的不可靠同样限制了攻击者**。报告提到模型有时会幻觉出并不存在的凭据，或者把公开信息当成窃取到的机密。完全自主的攻击目前仍受这一点制约。

对防御方的含义有两条。其一，侦察、漏洞利用、横向移动的速度和规模门槛正在下降，补丁窗口和检测响应时间需要按机器速度的对手来重新估计。其二，智能体平台的提供方需要承担滥用检测的责任——上述行动最终是被模型提供方通过行为监测发现并阻断的，这类检测能力应当成为选择平台时的考察项。

### 14.1.8 加固清单

以下清单汇总了本节的要点，可用于团队引入编码智能体时的安全评审：

```text
□ 运行环境
  □ 启用沙箱，文件系统与网络同时隔离；凭据文件不可读
  □ 跳过确认的模式只在沙箱或一次性环境中使用
  □ 云凭据、发布令牌不出现在智能体可达的环境变量和文件中

□ 仓库内容
  □ 规则文件与智能体配置纳入代码评审，并扫描不可见字符
  □ 打开不熟悉的仓库时不自动加载其中的配置、钩子与 MCP 服务
  □ 配置文件、钩子目录、Shell 启动文件对智能体只读

□ 生成的代码
  □ 新增依赖经过存在性与信誉校验，安装脚本默认不执行
  □ 依赖声明、构建脚本、持续集成配置的修改强制人工评审
  □ 智能体提交的变更与人类贡献适用同一评审标准
  □ 智能体产出的代码与提交先过密钥扫描（Gitleaks、TruffleHog 一类，见 8.4），再进入评审

□ 分发与更新
  □ 智能体、扩展与 MCP 服务固定版本，验证后再升级
  □ 仅从可信来源安装，校验发布者与签名

□ 持续集成
  □ 不可信事件触发的任务只持有只读令牌，不接触密钥
  □ 读取不可信内容的任务与执行写操作的任务分离
  □ 不与发布流水线共享缓存与运行环境

□ 审计
  □ 记录智能体读取的文件、执行的命令与出站请求
  □ 组织层面集中管理权限与沙箱策略，仓库配置不能放宽
```

> **本节要点**
> - 编码智能体默认三项齐全，而且产出的代码会被执行，一次注入可以进入供应链。
> - 仓库里的每个文件都是提示：规则文件、Issue、依赖文档、命令输出都能携带注入；仓库内的智能体配置等同于可执行内容，打开仓库前不要让它生效。
> - 跳过确认的模式只能与沙箱和凭据隔离绑定使用；持续集成中读不可信内容的任务不得持有写权限。
